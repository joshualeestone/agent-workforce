# v029 -- 0.2.9, the first version a person can answer an agent from

**2026-08-21.** One line in this repo: `package.json` 0.2.8 to 0.2.9. Nothing
else in the tree carries the number, confirmed by grep, and the installer and
the build both parse it out of `package.json` at runtime
(`install/setup.sh:1350`, `tools/build-kosmos-bundle.sh:216`) rather than
hardcoding it, so `Info.plist` and the bundle's `VERSION` cannot drift from the
bump.

🛑 **BUT THE VERSION HAS A SECOND HOME AND IT IS NOT IN THIS REPO.**
`engine/update.js:82` fetches `latest.json` from the release host and compares
it against `require('../package.json').version`. **If the 0.2.9 bundle is
published and `latest.json` still reads 0.2.8, `newer()` returns false for every
installed copy and nobody is ever offered the update.** A release that ships the
artifact and forgets that file is silently invisible, which is the same shape as
the finding below: the number agrees with itself while the thing a person gets
does not move.

## Why now

🛑 **What is published is not what is on `main`, and the version number says
nothing about that.** Measured against the artifact the installer actually
fetches rather than inferred:

    curl -fsSL https://installkosmos.com/dist/kosmos-arm64.tar.gz | tar -xzO VERSION
    app:    e1fdeaf (package.json 0.2.8)
    built:  2026-08-20T05:41:31Z

`e1fdeaf` is the 0.2.8 bump itself, so **three PRs merged after it have never
shipped** (#105, #106, #107), and two large ones landed this morning (#119,
#128). A person installing today gets what they got yesterday.

🛑 **RETRACTED, and the retraction is more useful than the claim.** I reported
`kosmos-x64.tar.gz` as a 404 that "would bite an Intel Mac". It is neither a gap
nor reachable, on two independent counts, both verified:

1. **`install/setup.sh:974` refuses first.** `case "$ARCH" in arm64) ;; *) die
   "Kosmos needs a Mac with Apple silicon (M1 or newer). This Mac is $ARCH."`
   The comment above it says why in as many words: *"Without this an Intel Mac
   asks the CDN for a bundle that does not exist and the experience is a bare
   'Could not install Kosmos' after a 404. Say the real reason in a sentence."*
   So an Intel Mac gets a named sentence and never requests the file.
2. **`uname -m` returns `x86_64`, not `x64`.** Both the build
   (`tools/build-kosmos-bundle.sh:42`) and the installer (`setup.sh:970`) derive
   the name from it, so **the URL I tested is one no installer ever
   constructs**, guard or no guard.

📌 **I tested a URL instead of the code path that builds URLs**, and got a 404
that was real and meant nothing. Before calling something a defect, ask whether
somebody ruled it on purpose and whether the thing you probed is the thing the
product asks for. Caught by Mona Lisa.

## Pipeline after merge

Carried forward from `v028-20260820.md` rather than re-invented, because the
finding at the top of this plan is that publishing silently lagged `main` by
three PRs, and this chain is the recorded procedure that catches exactly that.

    build -> chaoskosmos-site dist/ -> versions.html -> vercel deploy --prod ->
    read latest.json AND the version inside the SERVED tarball, with the
    previous tarball as a positive control, and confirm the new markup is in
    the bundle.

⚠️ **`latest.json` must never appear before the artifact it points at.** The app
polls it every fifteen minutes (`engine/update.js:25`), so a deploy that
publishes the pointer first offers an update whose download is not there yet.
One deploy carrying the tarball, the installer and `latest.json` together makes
that impossible.

📌 **The positive control is not ceremony.** Reading the served tarball proves
the new one is up; reading the PREVIOUS one proves the read is capable of
telling them apart. Without it, a cached or unchanged response looks identical
to a successful publish.

## What this does NOT do
