## 2. The honesty problem, which is the actual design work

Adding an agent to a project must be worth doing — *"otherwise there's no real point in
just seeing that I made an agent, it's kind of useless."* A record that changes nothing
is a label. So membership does something real: **Kosmos writes the project's folder into
that agent's instruction file.**

That produces four claims, and only three of them are true. Naming which is which is
the whole job, because every real defect this codebase has produced is one shape — *a
screen asserting a state nobody checked.*

| Claim | True? | What the UI may therefore say |
|---|---|---|
| This project is that folder | ✅ checkable — we can stat it | the folder path, and whether we can read it |
| These agents are on this project | ✅ it is our own record | "Mara and Nils are on this" |
| We told this agent where the folder is | ✅ we wrote the line, we can show it | "Kosmos told Mara where this folder is" |
| This agent **knows** / **works in** / **can only touch** that folder | ❌ | **nothing.** Never. |

Three consequences that are requirements, not preferences:

1. **No boundary language anywhere.** No locks, no "access", no "restricted", no "can
   only". Membership is an organising fact (scope §5, requirements §4). *A level that
   is not enforced is worse than none, because it is believed.*
2. **A running agent does not see the change.** Claude Code reads its instruction file
   at session start. So the honest sentence is **"Mara will see this the next time she
   starts"** — not "Mara now knows". This is merged≠deployed, in the product. When
   restart ships (deficit #0) this becomes an offer; today it is a plain statement.
3. **Unreadable is not empty.** A project whose folder moved shows as unreadable, not
   dropped (scope §4 Q3). A member we cannot see shows as unknown, not as fine.

## 3. Object model

Extends nothing and invents nothing (scope §5). `Project` is the object §4 already
names; membership is the many-to-many the mock already draws.

```
Project {
  id         slug, derived via store.safeKey — untrusted, ends up in no path but is a key
  name       the user's words
  folder     absolute path
  agents     [sessionName]   ⚠️ MACHINE name, not display name
  createdAt, updatedAt
}
```

**`sessionName`, not `name`.** The two coincide for every agent Kosmos creates — which
is the only kind my tests would naturally use — and differ for exactly the pre-existing
fleet (`claudebot` displays as `Splinter`). This is the same field that shipped wrong in
Remove and was caught by a blind review. **Act on the machine name, speak the display
name.**

**Storage:** `projects.json` in the app-data root, write-then-rename, honouring
`AGENT_WORKFORCE_DATA`. Same shape and same atomicity as `writeProfile` and
`removed.json`. Nothing is written into the user's project folder, ever (§7b).

## 4. What gets built

### `engine/projects.js` (new file)
- `list()` — every project, each **stated against reality**: stat the folder
  (`readable` / `missing` / `unreadable`), and resolve each member against the live
  roster so a member we cannot see comes back `unknown` rather than being dropped.
- `create({name, folder, agents})` — validates the folder exists and is a directory.
- `update`, `addAgent`, `removeAgent`, `remove`.
- `projectsFor(sessionName)` — the reverse edge, for the agent detail panel (the mock
  draws three project names under agent 2).

### Instruction-file writing — the part that can eat someone's work
A **delimited managed block** appended to the agent's `CLAUDE.md`:

```
<!-- kosmos:projects:start -->
## Your projects
- Henderson lease — /Users/josh/work/henderson
<!-- kosmos:projects:end -->
```

Rewriting replaces only between the markers. **Tested by round trip**: user text above
AND below, rewrite, assert both survived verbatim; and a file with no block at all gets
one appended without disturbing what was there. Reuses `engine/instructions.js` rather
than opening a second way to write that file.

### Routes in `server.js`
`GET/POST /api/projects`, `GET/PUT/DELETE /api/project/:id`,
`POST/DELETE /api/project/:id/agent/:name`, plus `GET /api/folders?path=` for §5.
All writes sit behind the existing `crossSiteWrite` guard, which runs before every
route by construction.

### `GET /api/folders` — new safety code, therefore the least trustworthy code here
Read-only, directories only, **rooted at `$HOME`**, no dotfiles. Its guard must refuse:
`..` traversal, an absolute path outside `$HOME`, a symlink pointing out of `$HOME`
(resolve with `realpath`, then re-check), a null byte, and a path that does not exist.
Five of nine blockers in a previous loop were in guards I had just added; this one gets
attacked harder than the thing it guards.

### Screens (`web/index.html`)
1. **Empty** — the screen first-run hands you. One job: point at a folder you already
   have.
2. **List** — name, folder (with its readable state), the agents on it, what is
   happening. If we cannot read the agents, the row says we cannot see them; it does
   not say they are fine.
3. **One project** — the folder, its agents, add/remove, and the honest note that
   talking to them is not built yet.
4. **Add project** — two decisions, not a form (§4: this is a security-relevant
   screen): which folder, and which agents. Each carries its consequence in a sentence.
5. **Agent detail** — gains the projects it is on.
6. **Joint Projects** — unchanged placeholder, paywall disclosure intact.

### Folder picking, because a browser cannot give a real path
`<input webkitdirectory>` deliberately withholds absolute paths, so the only options
are "type a path" or "let the server list folders". Typing a path *is* the wall for the
audience §0 exists for, so: **a one-level-at-a-time browser rooted at `$HOME`**, plus a
typed path with real server-side validation for anyone who prefers it. This is why
`/api/folders` exists at all.

## 5. Testing

**New test files** — `engine/projects.test.js` and `server.projects.test.js`.
Deliberately NOT grown into `server.test.js`: PR #28 adds +516 lines there and +896 to
`web/index.html`, and the *restart* branch is parked to this day on exactly that kind of
test-union merge. Separate files make the union trivial.

Every test file sandboxes **all three** write roots (`AGENT_WORKFORCE_DATA`,
`_WORKERS`, `_LAUNCH`) at the top — an unsandboxed run does not litter, it takes live
fleet agents off the air.

Controls that are mandatory, each because it has already caught something real:
- **Assert presence before absence.** Before asserting a removed member is gone from a
  row, assert it was in the row. A vacuous assertion passes against code that filters
  nothing and code that filters everything.
- **Mutation-verify every guard.** Revert the fix, confirm the new test fails, put it
  back. Twice I have believed a guard was pinned when the patch never applied.
- **Test the display-vs-machine name split with a fixture where they differ**, since a
  fixture where they agree cannot fail.
- **Round-trip the generated artifact**, not its text.
- **Browser check** — `docs/browser-checks/render-projects.js`, every state, light and
  dark. 316 tests and two blind reviews once passed a fully transparent modal because
  nothing had ever rendered the page.

## 7. Risks

| Risk | Handling |
|---|---|
| The managed block eats a user's instructions | delimited markers + round-trip tests both sides |
| `/api/folders` escapes `$HOME` | five explicit refusal tests, mutation-verified |
| Merge pain against PR #28 | new files for tests; shared files touched minimally |
| Membership reads as a permission | no boundary language; reviewed as its own pass |
| Claiming an agent "knows" | "next time she starts", everywhere it appears |
| Context ceiling mid-build | commit per increment; clean turn-end restart beats a mid-build one |
