## What is actually broken

Investigated before scoping, and it is worse than the request implies.

1. **`subscription.check()` is called exactly once, at `engine/firstrun.js:111`.** The
   board's `/api/status` has no subscription field (verified against the running board:
   `checkedAt`, `counts`, `agents`, `version`). `server.js` never mentions it. So Kosmos
   checks the connection during onboarding and never looks again.
2. **`idle` means both "waiting for work" and "cannot work".** Verified on the running
   board: 13 agents, exactly two states, `idle` (12) and `working` (1). An agent stranded
   by a broken sign-in produces no output and lands in `idle`, indistinguishable from a
   healthy one.

(2) is the one that matters, because it renders a dead agent as a healthy one, which is
the precise thing this codebase is built to prevent.

## The trap, and why the obvious fix is wrong

The obvious way to detect (2) is a new marker in `classify()` (`engine/status.js:938-1063`)
matching whatever Claude Code prints on auth failure.

**Nobody here has seen that output.** Writing that regex would be inventing a detector for
a screen nobody has looked at, which is the exact defect class this repo exists to prevent,
shipped into the mechanism meant to prevent it. It also inherits the fragility the
multi-provider audit documented: every marker is a claim about a UI we do not control, and
it would need re-doing per provider.

## The approach: derive, do not scrape

Compose two facts we can actually observe instead of guessing at a third.

1. **Ask the question on the tick.** `subscription.check()` on each status build.
2. **Report it as a machine-level fact** in `/api/status` under `connection`.
3. **Render it once at the top of the board.** A broken connection is one fact about the
   machine, not thirteen facts about thirteen agents. Per-card would bury it.
4. **Let the UI compose.** When the connection is not working, idle agents are rendered as
   possibly-blocked rather than as waiting.

Every future provider inherits this without anyone knowing its terminal output.

## ⚠️ The honesty constraint, which is the whole design

**When the connection is down we do NOT know that an idle agent is dead.** It might have
just finished. So the board must not assert it.

- The banner states the observed fact (the connection is not working) and that agents may
  be unable to start work.
- Idle agents are marked as *possibly affected*, never as dead.
- **`unknown` is not a failure.** `subscription.js` already distinguishes "no subscription"
  from "we could not read the file", each with a `because`. Rendering not-knowing as a
  confident failure would be the same defect in a new place. Three states, styled as three
  things.

Asserting "these 12 agents are dead" off one file read would be exactly the overreach this
feature exists to correct.

## Caching, and why it needs a test

`~/.claude.json` is **95,152 bytes** and the board ticks every **5 seconds**. Parsing 95KB
twelve times a minute forever is work nobody can see, which the README explicitly calls out
as the difference between a page that idles cool and one that spins a fan.

So: cache on `mtimeMs` plus `size`, re-read only on change.

⚠️ **This cache is new safety-adjacent code and therefore the least trustworthy code in the
diff.** Its failure mode is serving a stale `connected` after the connection breaks, which
would make this feature actively lie in exactly the case it was built for. Tests must cover:

- file changes on disk, verdict updates
- file **deleted**, verdict must become not-connected, never stale-connected
- file becomes unreadable, verdict must become `unknown` and not stale
- unchanged file is not re-parsed (assert the read count, do not assume)

## Verification

- `node --test` for the engine and cache behaviour, including the deleted and unreadable
  paths, with sandboxed `AGENT_WORKFORCE_CLAUDE_CONFIG`.
- **A rendered check**, not a text assertion: drive the board with a fake config in each of
  the three states and photograph what the reader sees. Text tests cannot see whether
  `unknown` was styled as a failure, which is the specific thing that would be wrong.
- Control first: assert the banner is **absent** when connected, then present when not.
  "The banner is showing" proves nothing unless the same check first proved it was not.

## Out of scope, deliberately

- Detecting auth failure from pane text. See the trap above. If it is ever wanted, it needs
  an observation first, not a guess.
- Multi-provider. This lands the shape; providers plug into it later.
