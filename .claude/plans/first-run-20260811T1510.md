# First-run screens + the routing that opens on them

Resumes the `first-run` branch after the engine work (`7ca5ddf` subscription,
`6dbf157` state-in-one-place, `baf91b4` routes). Everything below is the part a
person actually sees. Sources: `[[kosmos-launch-backlog]]` deficit #2,
`[[agent-platform-requirements]]` §125/§126/§868/§7b, and the drawn wireframe
`agent-platform-wireframes/screen7-firstrun-v2.png`.

## The flow, four steps

The wireframe says "Step 2 of 4" and captions the remainder ("Next: sign in to
Claude, then we will set up your first agent"). So the four are:

1. **Welcome** — what this is, that it runs here, that it asks for no account
   and no email (§69), and the §7b statement that a complete record of every
   conversation is kept on this machine. One Continue.
2. **Checking your computer** — the wireframe's centrepiece. Real checks, read
   from the machine, each able to answer *we cannot tell*.
3. **Connect Claude** — `engine/subscription.check()`, three answers.
4. **Your agents** — the adopt-or-create fork from `engine/firstrun.state()`.

Then it lands: on the board, or in the existing create flow.

## Calls made here, so they are not re-litigated

**1. `pmset -g` is the wrong file to read, and it is wrong on this machine right
now.** Measured:

    $ pmset -g
     sleep   0 (sleep prevented by Claude, caffeinate, powerd)

That block is *currently in use*, not *configured*. Something holding a
caffeinate assertion makes a Mac that sleeps after ten minutes report that it
never sleeps — and the assertion goes away when that process does. A check keyed
on it says "your agents will keep working" to somebody whose agents stop the
moment the caffeinate drops. Read `pmset -g custom`, which is the setting.

**2. A laptop has two answers and the second one is the one that bites.**
`pmset -g custom` prints an `AC Power` block always and a `Battery Power` block
only where there is a battery. So the presence of that block is how we know we
are on a laptop, and "sleeps on battery" is the case the wireframe's dashed note
is about. This Mac mini has no such block; the laptop path therefore cannot be
verified here, and the test fixtures carry a real laptop's shape rather than a
guess at one.

**3. No "Change this for me" button, against the wireframe.** Changing the sleep
setting is `sudo pmset`, and this server runs as the user with no way to ask for
a password. A button that offers it and then cannot do it is precisely the shape
this codebase is built against — a screen asserting something nobody checked.
The check tells them what it found and where to change it. **Documented as a
deliberate deviation from the drawn screen**, not an omission.

**4. First run never blocks.** Every step continues, including the one that says
we could not tell, and including "no subscription". §125 says guide, do not
error. The only thing that changes is what the screen says.

**5. It is an overlay, not a tab.** The board is behind it, and a person part
way through setup must not be able to click into Settings. But an overlay with
no exit is a trap if the detection is ever wrong, so there is a way out on every
step, and taking it marks first run seen — the flag means *seen*, not
*completed successfully*.

**6. Fails closed on the fetch.** If `GET /api/first-run` fails, the overlay does
not appear. (An earlier draft of this plan called the same behaviour
"fail-open", which is the opposite label for the identical decision — the
action being refused is *showing onboarding*, so refusing it is closed.) Showing onboarding over somebody's working board because we could
not read a flag is the same mistake as `engine/firstrun.seen()` already avoids
one layer down.

**7. `?first-run=1` forces it open.** The only way to screenshot it on a machine
that has already been through it, and this file already deep-links every other
panel for the same reason.

## What gets built

- `engine/machine.js` — the three checks, each returning `ok` / `attention` /
  `unknown` with a sentence. Fixture-driven: the `pmset` output is injected so
  the tests never depend on the operator's power settings.
- `GET /api/machine` — the route.
- `web/index.html` — `#panel-firstrun`, four steps, the routing, the CSS.
- Tests: engine unit tests with real captured `pmset` output (desktop, laptop,
  laptop-that-sleeps, unparseable), route tests, and `pageFunction` tests on the
  render functions.
- **Rendered, not just asserted.** Text tests passed a fully transparent modal
  once. Every screen gets opened in a real browser and screenshotted into
  `docs/screenshots/firstrun-*.png` before the PR.

## Order

1. `engine/machine.js` + tests + route.
2. The screens + routing + CSS.
3. Render each state in a browser, screenshot, fix what only rendering shows.
4. Challenge loop, then PR with the screenshots.
